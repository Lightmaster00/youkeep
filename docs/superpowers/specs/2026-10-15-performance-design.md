# Performance pass — Design

**Status:** Approved in chat (2026-10-15). User report: the app is "really slow sometimes", especially **during downloads** and **when a page loads**. Measured on a synthetic library (10k videos, 20k tracks, 8k episodes) every API answers in < 80 ms and the JS bundle is small (1.2 MB), so steady-state server cost is not the problem. Leads: (1) every yt-dlp progress line triggers a synchronous SQLite commit with no `synchronous` pragma (default FULL = an fsync wait per commit, blocking the whole Node event loop; harmless on a Mac SSD, painful on a busy Unraid disk); (2) the `*_au` FTS triggers fire on EVERY update of a row (videos, music_tracks, podcast_episodes) and re-index the full description on each progress tick (0.25 ms vs 0.006 ms measured); (3) thumbnails are served full size (100–300 KB) into ~300 px cards.

## Goals
Smooth UI while downloads run; lighter page loads; and a way to SEE event-loop stalls on the real server.

## Changes
1. **SQLite pragmas** (`server/utils/db.ts`): keep WAL; add `synchronous = NORMAL` (safe in WAL: no corruption, at worst the last transactions after a power cut), `temp_store = MEMORY`, `cache_size = -20000` (≈20 MB), `mmap_size = 134217728`, `wal_autocheckpoint = 1000`. Pragmas applied on the shared connection only; tests keep working.
2. **Throttle progress writes** (video `downloader.ts` progress parser, music and podcast downloaders' equivalents): a small helper `createProgressWriter(write)` that persists at most once per second per item and only when the displayed percent/speed/eta changed, always flushes on completion/failure/pause/cancel, and never writes after the item left `downloading`. Hoist the `db.prepare(...)` statements out of the per-line handler.
3. **FTS triggers only when indexed columns change**: recreate `videos_au`, `music_tracks_au` (and the podcast episodes equivalent if any) as `AFTER UPDATE OF <indexed columns>` triggers (videos: title, description, channel_id; music tracks: title, artist_id, album_id, genre; episodes: title, description, show_id), via an idempotent migration (DROP TRIGGER IF EXISTS + CREATE) guarded by a settings flag `fts_triggers_v2` so it runs once. Behaviour of search must not change (test: renaming a title re-indexes; a progress update does not touch the FTS content rows).
4. **Resized, cached thumbnails**: `GET <existing thumbnail url>?w=<160|320|480|640|960>` (whitelist; other values → original). The downloads route generates `data/cache/thumbs/<sha1(path+mtime+size)>-<w>.jpg` on first request with `ffmpeg -i <src> -vf scale=<w>:-2 -q:v 5 <out>` (async spawn, dedupe concurrent identical requests, max 2 concurrent ffmpeg, 10 s timeout, atomic write via temp+rename), serves it with the same auth/containment rules as the original and `Cache-Control: private, max-age=31536000, immutable`; on any failure serve the original. Never upscales (if the source is narrower, serve the original). Same authorization path as the original file (no new oracle). Cache dir is excluded from library wipes/tidy and can be deleted safely; a startup sweep removes cache files older than 90 days.
   - Client helper `app/utils/thumb.ts` `thumbUrl(path, width)` (adds `?w=` only for local `/downloads*` URLs; external URLs unchanged) used by `VideoCard` (480), `MusicTrackCard`/`PodcastEpisodeCard`/`MusicAlbumTile`/artist tiles (320), `MusicTrackList` rows and queue lists (160). Add `decoding="async"` and explicit `width`/`height` (or aspect-ratio CSS) on card images to avoid layout shift; keep `loading="lazy"` except above-the-fold hero images (`fetchpriority="high"`).
5. **Event-loop stall monitor**: `server/utils/loopMonitor.ts` using `perf_hooks.monitorEventLoopDelay` (resolution 20 ms), sampled every 10 s; keeps a 15-minute ring of `{ at, maxMs, p99Ms }`; logs `[perf] event loop stalled: max=…ms p99=…ms` when max > 250 ms (at most once per 30 s); `GET /api/admin/system/perf` → `{ current: {maxMs,p99Ms}, last15min: { maxMs, p99Ms, stalls }, activeDownloads }`; a one-line "Server responsiveness" readout in Settings → System → Tools & logs (`ServerResponsivenessPanel.vue`): green/amber/red by max delay (<100 / <500 / ≥500 ms) with the last-15-minutes numbers and a note "Stalls while downloading usually mean the data folder is on a slow disk — keep appdata on an SSD/cache drive."
6. **Small wins found on the way** (do only if trivial and covered by tests): hoist other per-event `db.prepare` in hot paths touched by the above; `Cache-Control` for `/api/*` GETs stays unchanged.

## Out of scope
UI redesign (next spec), worker threads / moving SQLite off the main thread, changing the polling cadence (already adaptive).

## Testing
- Unit: `createProgressWriter` (throttle window, changed-only, flush on finish, no write after leaving downloading, fake timers); `thumbUrl`; width whitelist; loop monitor ring/threshold logic (with an injectable histogram).
- Integration: pragmas applied (`PRAGMA synchronous` = 1 on a file DB created through the real init path); trigger migration idempotent and search still correct (rename re-indexes; progress update does not change the FTS content row — compare `rowid`s / `videos_fts_content` before/after); thumbnail route: generates once, second hit served from cache, whitelist, no upscale, auth/containment parity with the original, failure falls back to original, concurrency dedupe (ffmpeg spawn injected, no real ffmpeg in tests), cache sweep; `/api/admin/system/perf` admin-only.
- Component: responsiveness panel states; cards use `?w=`.
- **Benchmark evidence** (controller, not a test): before/after on the synthetic library — UPDATE-progress cost, event-loop lag under a simulated progress storm (e.g. 8 writers × 10 updates/s through the real handler code path) and bytes transferred for the home page image set.
